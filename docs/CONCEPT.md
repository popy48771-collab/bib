# 本棚スキャナ — 構想

本から書誌情報を読み取り、蔵書一覧を生成するアプリ。
GitHub Pages（静的ホスティング）で動作させることを前提に設計する。

> **この文書は設計の背景（なぜそう決めたか）を残すためのもの。**
> 現時点で何が動くかは [CLAUDE.md](../CLAUDE.md) と [README.md](../README.md) が正。
> 検討したが採らなかった道もそのまま残してある。現状との対応は次のとおり。
>
> - **方式A（Tesseract.js によるローカルOCR）** — **採った。ただし構成が違う。**
>   ここでは「棚の写真を撮り、OpenCV.js で背表紙の縦境界を検出して短冊に切る」としているが、
>   実装は**画面中央の読取レーンを通った1冊だけを取り込む**方式にした。境界検出そのものが
>   不要になり、OpenCV.js（8MB超）を入れずに済む（CLAUDE.md §2「背表紙の決定」）
> - **方式B（VLM に写真を渡す）** — 一度実装したが撤去した。設定画面を廃したため
>   BYOK のキー入力口が無くなり、構成できなくなったため（§3, §4）。
>   端末内OCRの精度が足りないと実測できたときの次の手として残してある
> - **チャットAI に読ませて結果を貼る経路** — 撤去した。写真の添付と結果の貼り戻しが
>   手作業で、「かざすだけ」という本筋から外れていたため
>
> **バーコードと背表紙の両方が動く。** 棚の静止画から複数の背表紙を一度に切り出す方式
> （§3 方式A の元案、Phase 3）は、レーン方式で精度を測ってからの拡張とする。

---

## 1. 何を作るのか

**入力**: 本棚の写真（撮影 or アップロード、複数枚可）
**出力**: 確認済みの書誌一覧（CSV / JSON / Markdown / BibTeX / ISBNリスト）

一言でいえば「本棚に向けて数枚撮れば、蔵書リストができる」。

### 想定する使い方

- 引っ越し前の蔵書棚卸し
- 「この本持ってたっけ？」を出先で引けるようにする
- 蔵書リストをブクログ・読書メーター等へ流し込む
- 研究室・部室・実家の本棚の記録

---

## 2. 処理の全体像

```
撮影 ──▶ 背表紙の切り出し ──▶ 文字認識 ──▶ 書誌同定 ──▶ 人間の確認 ──▶ 出力
 (1)         (2)              (3)         (4)          (5)         (6)
```

各段階の難易度は均等ではない。**(3) 文字認識と (5) 人間の確認が全体の品質を決める。**

| 段階 | 難易度 | 備考 |
|---|---|---|
| (1) 撮影 | 易 | ただし解像度・ブレ・照明が下流すべてを支配する |
| (2) 切り出し | 中 | 縦エッジ検出。VLM方式なら不要 |
| (3) 文字認識 | **難** | 縦書き日本語＋装飾書体＋箔押し＋回転 |
| (4) 書誌同定 | 中 | 誤字を含む文字列からの曖昧一致 |
| (5) 確認 | **要設計** | ここを速くできるかがアプリの価値 |
| (6) 出力 | 易 | |

## 3. 最大の設計判断 — 文字認識をどうするか

背表紙OCRは、一般的な文書OCRよりはるかに難しい。

- 縦書き（横向きに90°回転している）
- 明朝・ゴシックだけでなく、筆文字・デザイン書体・箔押し・エンボス
- タイトル・著者・出版社・レーベルが混在し、文字サイズもバラバラ
- 薄い本は文字が潰れる、奥の列は写らない、光の反射で飛ぶ

これに対する現実的な選択肢は3つある。

### 方式A: 古典的CV + Tesseract.js（鍵なし・完全ローカル）

OpenCV.js で背表紙の縦境界を検出して短冊に切り、90°回転させて Tesseract.js の `jpn_vert` にかける。

- ✅ APIキー不要、通信なし、無料、オフライン動作
- ❌ 日本語背表紙での実効精度は低い（タイトル完全一致は体感で半分以下）
- ❌ traineddata が数十MB、初回ロードが重い
- 前処理（グレースケール化・適応的二値化・傾き補正・コントラスト補正）が精度を大きく左右する

### 方式B: VLM（マルチモーダルLLM）に一発で解かせる — **推奨**

写真をそのままモデルに渡し、「写っている本のタイトル・著者・出版社をJSON配列で返せ」と指示する。
切り出し・回転・OCR・正規化を**すべてモデルが同時に処理する**。

- ✅ 精度が段違い（鮮明な写真なら実用水準）
- ✅ 実装が圧倒的に軽い（画像 → JSON、それだけ）
- ✅ 「装丁から推測して補完する」といった人間的な読み方ができる
- ❌ APIキーが要る
- ❌ **存在しない本を捏造しうる**（後述の対策が必須）

### 方式C: ISBNバーコード（救済用）

背表紙が読めなかった本は、裏表紙のバーコードを1冊ずつ撮る。精度は事実上100%。
`BarcodeDetector` API（対応ブラウザ）、非対応環境は ZXing-wasm でフォールバック。

### 結論

> **方式Bを主軸に据え、方式Aを「鍵なしでも触れるモード」として残し、方式Cを取りこぼしの救済に使う。**

## 4. GitHub Pages という制約と、BYOKという答え

GitHub Pages は**静的ホスティングであり、秘密を持てない**。
サーバーサイドが無い以上、APIキーをアプリ側に埋め込めば全世界に公開されるのと同じ。

したがって方式Bを採るなら、答えは一つしかない。

### BYOK（Bring Your Own Key）

利用者が自分のAPIキーを設定画面に貼り、`localStorage` に保存して、
**ブラウザから直接** モデルプロバイダのAPIを呼ぶ。キーはどこにも送信されない。

個人用ツールとしてはまったく妥当な設計で、しかも運用コストがゼロになる（各自が自分の分を払う）。

**ブラウザ直叩きの可否（調査結果）**

| プロバイダ | ブラウザから直接呼べるか |
|---|---|
| Anthropic | ✅ `anthropic-dangerous-direct-browser-access: true` ヘッダで公式にサポート |
| Google Gemini | ⚠️ `?key=` 形式の素の `fetch` なら概ね可。公式JS SDKは独自ヘッダがpreflightで弾かれる報告あり → SDKを使わず生fetchで叩く |

コストは1枚あたり数円以下のオーダーで、蔵書棚卸しのような一過性の用途なら問題にならない。

### 二段構えのUX

初回訪問時にキーは要求しない。**キーなしでも方式A（Tesseract.js）で動く**状態にしておき、
「精度を上げたい人だけキーを入れる」導線にする。これで「まず触れる」と「本気で使える」を両立する。

## 5. 書誌情報の検索先

背表紙からはISBNが得られない。**文字列（しかも誤字入り）から書誌を引き当てる**必要がある。

各APIをブラウザから直接呼べるか、実際に検証した。

| API | CORS | 検索方法 | 日本語カバレッジ | 評価 |
|---|---|---|---|---|
| **Google Books** | ✅ **実測で確認済** | タイトル・著者・ISBN | 中 | 静的サイトから使える唯一の全文検索。**主軸** |
| **openBD** | ✅ ブラウザ利用前提の設計 | **ISBNのみ** | 高（新しめの本） | タイトル検索ができない → **ISBN確定後のエンリッチ専用** |
| **NDLサーチ** | ❌ **CORSヘッダなし** | タイトル・著者・ISBN | **最強・最も権威的** | GitHub Pages から直叩き**不可** |

### ここが本アプリ最大のトレードオフ

日本語書籍の同定精度を最も上げてくれる NDLサーチが、まさに静的サイトから使えない。
取りうる道は3つ:

1. **使わない** — Google Books のみで妥協する（Phase 1 はこれ）
2. **極小プロキシを置く** — Cloudflare Workers 等の無料枠にCORS中継だけ置く。「GitHub Pages 単体」からは半歩出るが、秘密情報は不要なので運用は軽い（Phase 3 の推奨）
3. **事前に索引を焼き込む** — GitHub Actions で書誌データを取得し静的JSONとして配信。全件は非現実的だが、部分索引なら余地はある

### 検索の流れ — 1冊ごとに自動で追いかける

当初は**段階ごとにボタンで進める**設計にしていた。一次照合の結果を見てから
NDL も当てるか決められる、という考えだったが、実際に使うと逆に働いた。

**バーコードで読んだ本は、人間が判断できることが何も無い。** ISBN は完全一致で
引けるので、出てきた書誌をそのまま採るしかない。それでもボタンを押させると
「読んだのに一覧が空」という状態が生まれ、押し忘れれば成果はゼロになる。

そこで**1冊入ってきたら、書誌が埋まるまで自動で追いかける**方式に変えた。

```
バーコードを読む ──▶ ISBN だけの行が即座に一覧へ
       │
       ▼  （以降は自動。ボタンは無い）
   openBD ──当たり──▶ 確定
       │外れ
       ▼
 Google Books ──当たり──▶ 確定
       │外れ
       ▼
  NDLサーチ ──当たり──▶ 確定
       │外れ
       ▼
   「見つからず」として残す（読んだ ISBN は捨てない）
```

当たった時点で打ち切る。外れたときだけ次のソースへ回るので、
待ち時間もリクエスト数も、当たりやすいソースから順に並べた分だけ短くなる。
日本語書籍は openBD が最も速くよく当たり、Google Books は和書に弱いが洋書に強く、
NDL は法定納本ぶん網羅性が最も高い。この順序はそのカバレッジの差から来ている。

#### 段階を分けて得ていた性質は、そのまま保つ

ボタンを外しても、段階実行が持っていた設計上の利点は失いたくない。
これらは実装上の不変条件として単体テストで保証している。

| 性質 | どう保つか |
|---|---|
| **失敗の隔離** | あるソースが落ちても例外を飲んで次のソースへ回す。1冊の失敗が他の冊に波及しない |
| **非破壊** | 後のソースは前の候補を消さず `candidates` に足す。空振りした記録も残す |
| **冪等** | 同じ項目を再照合しても結果が壊れない。引けなかった項目は後から引き直せる |
| **尊重** | 利用者が手で確定したもの（`pinned`）と除外したものには一切触れない |
| **中断と再開** | 状態は IndexedDB に残るので、いつ閉じても続きから読める |

> **注意**: 自動化しても NDL の CORS 制約自体は消えない。ブラウザから直接叩けないのは変わらず、
> 中継は依然必要である（§4 / `proxy/ndl-worker.js`）。

#### 突合の振る舞い（非破壊）

書名で引く経路（背表紙）では、NDL は一次結果を**上書きしない**。

- NDL の候補は `candidates.ndl` に**追加**する（Google Books の候補は消さない）
- 一次結果と食い違えば `conflicts` に記録し、状態を `差分あり` にして人間に見せる
- 一次結果に**欠けている**項目（出版年・ISBN等）だけを NDL の値で補完し、出典を記録する
- 一次照合で**見つからなかった**ものは、NDL でヒットすれば昇格させる

ISBN で引く経路（バーコード）では突合をしない。**完全一致なので比べる相手が無い。**

### 曖昧一致

OCR結果は必ず汚れている。素の完全一致では歯が立たない。

- **正規化**: 全角/半角、ひらがな/カタカナ、旧字体/新字体、長音・中黒、空白除去
- **スコアリング**: N-gram 類似度 + レーベンシュタイン距離
- **候補は1件に絞らない**: スコア付きで複数提示し、最終判断は人間に渡す

### VLMの捏造への対策

方式Bには「それらしい本を発明する」リスクがある。これを構造で潰す。

> **VLMの出力を最終結果として扱わない。必ず書誌DBで実在確認したものだけを確定済みとする。**

書誌DBでヒットしなかった項目は「未確認」として明示的に区別し、リストに紛れ込ませない。

## 6. UI/UX — 実はここが本体

**認識率100%は原理的に達成できない。** だから「全自動」を目指す設計は必ず失敗する。
目指すべきは **「人間が高速に確認・修正できること」**。

### トリアージ方式

```
┌─────────────────────────────┐
│  [ 本棚の写真 ]              │
│   ┌──┐┌──┐┌──┐┌──┐┌──┐      │  ← 背表紙にボックスをオーバーレイ
│   │緑││緑││黄││緑││赤│      │     緑=高信頼(自動確定)
│   └──┘└──┘└──┘└──┘└──┘      │     黄=要確認  赤=読めず
└─────────────────────────────┘
        32冊中 28冊確定  ████████░░
```

- 高信頼のものは**黙って自動確定**する。全件確認させない
- 人間が触るのは黄と赤だけ
- ボックスをタップ → 候補カード → 「これ」/「候補から選ぶ」/「手入力」/「除外」
- 赤（読めず）は方式C（バーコード）へ誘導

### 複数枚の統合

本棚は1枚に収まらないし、収めると解像度が足りない。**1段ずつ撮る**のが正しい運用。

- 撮影ごとに結果を蓄積し、ISBN と正規化タイトルで**重複排除してマージ**
- 棚の端が重複して写るのは前提として扱う

### 撮影ガイド

下流の精度は撮影で決まるので、ここに投資する価値が高い。

- 背表紙が画面いっぱいになる距離を促すガイド枠
- ブレ・暗さの警告
- 「棚1段ずつ、正面から」の初回オンボーディング

## 7. 技術スタック

| 領域 | 選定 |
|---|---|
| ビルド | Vite + TypeScript |
| UI | React（または軽量なPreact） |
| カメラ | `getUserMedia` / `<input type="file" accept="image/*" capture>` |
| 画像処理 | OpenCV.js（方式A時のみ遅延ロード） |
| OCR | Tesseract.js `jpn` + `jpn_vert`（方式A） |
| VLM | 生 `fetch`（SDKは使わない。preflight回避のため） |
| バーコード | `BarcodeDetector` → ZXing-wasm フォールバック |
| 保存 | IndexedDB（写真・認識結果）/ localStorage（設定・APIキー） |
| 配信 | GitHub Actions → GitHub Pages |
| PWA | Service Worker でオフライン起動・ホーム画面追加 |

**重いもの（OpenCV.js / traineddata）は必ず遅延ロードする。** 初回表示を殺さない。

### プライバシー

- 既定ではすべてブラウザ内で完結。写真はどこにも送られない
- 方式B使用時のみ画像がモデルプロバイダに送信される旨を、設定画面で明示する
- サーバーを持たない＝こちら側に蔵書データが一切残らない

## 9. 開発ロードマップ

### Phase 0 / 1 — 実装済み ✅
静的サイトの骨組み、BYOK設定、VLMによる背表紙抽出、Google Books 照合、
段階実行パイプライン（NDL突合・openBD補完を含む）、確認UI、5形式の出力、
IndexedDB永続化、GitHub Actions によるPagesデプロイ。

### Phase 2 — 鍵なしでも動かす
OpenCV.js による背表紙切り出し + Tesseract.js。バーコードによる救済。

### Phase 3 — 精度と体験
写真上のバウンディングボックス表示、書影表示、複数枚マージの重複排除、PWA化、撮影ガイド。

### Phase 4 — 計測
自分の本棚で正解データを作り、**再現率・適合率を実測する**。
体感でなく数字で議論できるようにして初めて改善が回る。

## 10. リスクと未解決の論点

| リスク | 対応方針 |
|---|---|
| 物理的に読めない本（薄い・傾き・反射・奥の列） | 原理的限界。バーコード/手入力へ素直に逃がす |
| VLMの捏造 | 書誌DBでの実在確認を必須にする（§5） |
| NDLが使えない | Phase 1 は Google Books で妥協 → Phase 3 でプロキシ |
| Google Books の日本語カバレッジ不足 | Phase 4 の実測で影響を数値化してから判断 |
| Google Books のレート制限（IP単位） | クライアント側でスロットリング、失敗時リトライ |
| 初回ロードが重い | 遅延ロード徹底、Phase 0 を軽量に保つ |

### 未検証の前提

実装環境から一部のドメインへの到達が遮断されていたため、以下は**公開仕様に基づく実装であり実地確認が未了**。
初回接続時に必ず生のレスポンスを確認すること。

| 項目 | 状況 |
|---|---|
| Google Books の CORS | ✅ 実測確認済（`github.io` オリジンに `access-control-allow-origin` が返ることを確認） |
| NDLサーチの CORS 非対応 | 調査で確認。実測は未了（ドメイン到達不可） |
| **NDL OpenSearch のレスポンス解析** | ⚠️ **未検証**。名前空間接頭辞の揺れに耐えるよう防御的に実装し、フィクスチャで単体テスト済みだが、実レスポンスとの突き合わせが必要 |
| openBD の CORS | 公式にブラウザ利用前提の設計。実測は未了 |
| Gemini のブラウザ直叩き | 生 fetch なら概ね可という調査結果に基づく。実測は未了 |

### まだ決めていないこと

- 方式Aは**そもそも実用水準に届くのか** — Phase 2 着手前に実データで小さく検証すべき
- 背表紙の切り出しをVLMにやらせて、切り出し後の短冊だけを再度モデルにかける**二段構え**は精度に見合うか
- 複数枚マージの重複判定を、どこまで自動化してよいか（誤マージは取りこぼしより痛い）

## 11. まず何から作るか

**Phase 0 → Phase 1 の順で、Phase 1 到達をもってMVPとする。**

理由は、Phase 1 の構成（VLM + Google Books + 確認UI）が、
**この構想全体で最も不確実な部分＝実際どれくらい読めるのか、を最短で検証できる**から。
方式Aの作り込みは、それが分かってから判断すればよい。
