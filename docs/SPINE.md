# 本棚スキャナ — 背表紙経路の設計

本棚にカメラをかざし、背表紙を読み取って書誌一覧を出す経路の設計。

> **この文書は「まだ実装されていないもの」の設計である。**
> 確定した判断は [CLAUDE.md](../CLAUDE.md)、いま何が動くかは [README.md](../README.md) が正。
> ここに書いた数値は**すべて未実測の目標値**であり、根拠は §13 の実測で作る。

合流点は既に用意されている（CLAUDE.md §2）。`ExtractedSpine` を作れれば、
そこから先の照合・一覧化・書き出しはバーコード経路と共通のものに乗る。
**したがってこの経路で新しく設計すべきなのは「映像 → `ExtractedSpine[]`」の一区間だけ**であり、
残りは既存部品の順序と統合規則の調整で済む。

## 0. 結論 — 足すもの

| # | 足すもの | なぜ |
|---|---|---|
| 1 | **ブラウザ内 OCR エンジン**（差し替え可能な口の裏に置く） | ML Kit は Web から呼べない（§1）。第一候補は PP-OCRv5 + onnxruntime-web（§2） |
| 2 | **自動シャッター**（静止＋鮮鋭度で1枚だけ選ぶ） | 毎フレーム OCR は端末が持たない。ボタンも置けない（§4） |
| 3 | **検出枠のクラスタリング**による背表紙の切り分け | OpenCV.js を入れずに切り出す（§5） |
| 4 | **向きの推定**（90°回転 / 縦書き） | 背表紙は必ず縦。ここを外すと OCR が全滅する（§6） |
| 5 | **OCR行 → 照合クエリの組み立て** | 書名・著者・出版社・レーベルの推定。照合精度の半分はここで決まる（§7） |
| 6 | **重複統合**（同じ背表紙を何度も読む前提） | パンすれば同じ本が何度も入る。行が増えては困る（§9） |

```
映像 ──▶ 自動シャッター ──▶ OCR(det+rec) ──▶ 枠のクラスタリング ──▶ クエリ組み立て
 (§4)      1枚だけ選ぶ        (§2/§6)          背表紙1本＝1クラスタ      (§7)
                                                    (§5)                  │
                                                                          ▼
                                                              ExtractedSpine[]
                                                                          │
                        ┌─────────────────────────────────────────────────┘
                        ▼        ここから先は既存（合流点）
                 重複統合(§9) ──▶ entriesFromExtraction ──▶ resolveByTitle(§8) ──▶ 一覧
```

**変更ではなく追加が主で、既存経路には手を入れない。** 唯一の例外は §8（`resolveByTitle` の
ソース順序）で、これはバーコード経路の挙動を変えない。

## 1. ML Kit は Web から使えない

提示された [ML Kit Text Recognition v2](https://developers.google.com/ml-kit/vision/text-recognition/v2?hl=ja)
は、狙いとしては正しい。**端末内で動き、無料で、日本語スクリプトに対応している** —
このアプリが欲しいものそのものである。

問題は配達手段だけである。**ML Kit は Android と iOS のネイティブ SDK であり、
Web / JavaScript 向けの実装は提供されていない。**
React Native や Flutter のプラグインは存在するが、いずれもネイティブ SDK の橋渡しであって、
ブラウザで動くものではない。

つまり ML Kit を使うということは、**このアプリを「URLを開けば使えるもの」から
「インストールするもの」へ変える**という判断とセットになる。読み取り精度の話ではなく、
配布形態の話である。

同類の「ブラウザから呼べそうで呼べないもの」も先に潰しておく。

| 手段 | 可否 |
|---|---|
| ML Kit（Web/JS） | 提供されていない |
| `TextDetector`（Shape Detection API） | Chrome で出荷されなかった。`BarcodeDetector` と違い当てにできない |
| iOS のライブテキスト / Google レンズ | 端末機能。Web ページから起動も取得もできない |

## 2. では何で読むか

**判断の枠組み: 「URLを開けば使える」を守れるか、で二分する。**
守れる範囲で当たるならそれが最良で、守れないなら §1 の配布形態の話に戻る。

| 手段 | 鍵 | 課金 | 初回DL | 日本語背表紙 | URLを開けば使える |
|---|---|---|---|---|---|
| **PP-OCRv5 + onnxruntime-web** | 不要 | 0 | 大（§3） | 中〜高（未実測） | ✅ |
| Tesseract.js（`jpn` / `jpn_vert`） | 不要 | 0 | 中 | **低**（CONCEPT §3 方式A） | ✅ |
| Chrome 内蔵の Prompt API（端末内 VLM） | 不要 | 0 | 極大 | 高 | ⚠️ デスクトップ中心。棚にかざす用途と合わない |
| クラウド OCR / VLM（Cloud Vision 等） | **要** | 従量 | 0 | 高 | ⚠️ §2「設定画面を持たない」と衝突 |
| ML Kit（ネイティブ殻） | 不要 | 0 | アプリ | **最高** | ❌ インストールが必要 |

### 決定

> **`OcrEngine` という差し替え可能な境界を1枚置き、その裏の第一実装を
> PP-OCRv5（onnxruntime-web）にする。**

理由は3つ。

1. **Tesseract.js は最初から負け筋である。** CONCEPT §3 が方式A について
   「日本語背表紙での実効精度は低い（タイトル完全一致は体感で半分以下）」と書いている。
   縦書き＋装飾書体＋箔押しは Tesseract の最悪ケースで、ここが駄目なら下流の照合をどう作っても無駄になる。
   PP-OCRv5 は日本語と縦書きを1つのモデルで扱うと謳っており、**勝ち筋があるのはこちら**。
2. **鍵を要求する手段は採れない。** CLAUDE.md §2 で設定画面を廃した結果、鍵の入力口が無い。
   VLM 経路が撤去されたのと同じ理由で、クラウド OCR もそのままでは構成できない。
3. **境界を置けば、この判断を間違えても捨てるのは実装1つで済む。**
   `OcrEngine` の口が同じなら、Tesseract.js への差し替えも、
   将来ネイティブ殻に移って ML Kit を裏に置くことも、上流（§5〜§9）を書き直さずにできる。

```ts
// src/lib/ocr/engine.ts — 唯一の口。上流はこれしか知らない
export interface OcrLine {
  text: string
  /** 4点。映像・写真上の 0..1 相対座標。回転した枠を表せるよう矩形にしない */
  quad: readonly [Point, Point, Point, Point]
  /** エンジンの自己申告信頼度 (0..1) */
  confidence: number
}

export interface OcrEngine {
  readonly kind: 'paddle' | 'tesseract'
  /** 1枚から行を取り出す。前処理・回転・認識はすべてこの中 */
  recognize(image: ImageData, signal?: AbortSignal): Promise<OcrLine[]>
  dispose(): void
}
```

**モデルと wasm は遅延ロードする。** 背表紙タブを開いて初めて取りに行く。
バーコード経路の初期表示に1バイトも足さない（zxing-wasm と同じ扱い。CLAUDE.md §2）。

### 記録しておく — 「秘密を持てない」のは Pages だけである

CLAUDE.md §1 は「GitHub Pages は秘密を持てない」と書いているが、
**同梱の Cloudflare Worker は秘密を持てる。** NDL 中継が秘密を持たないのは
鍵の管理を避けるための選択であって、不可能だからではない。

つまり技術的には「Worker に Cloud Vision の鍵を置き、そこへ画像を中継する」は成立する。
採らない理由は秘密の置き場ではなく、**費用と濫用**である。

- 従量課金を管理者が全員分払う。棚1枚あたりの単価が低くても、公開URLでは上限が読めない
- 画像を中継するということは、蔵書の写真が一度こちら側を通る。
  「こちら側に一切残さない」（CLAUDE.md §1）が濁る

**この2つが解けない限り採らない。** ただし「Pages だから無理」という理由付けは誤りなので、
将来これを再検討するときに §1 を根拠にしないこと。

## 3. GitHub Pages 固有の壁 — スレッドと、書影との衝突

**この経路で最初にぶつかるのは精度ではなく、たぶんこれである。**

wasm のマルチスレッド実行には `SharedArrayBuffer` が要り、それには
`Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy`
のレスポンスヘッダが要る。そして
**GitHub Pages は任意のレスポンスヘッダを設定できない。**

結果、素の GitHub Pages では **OCR はシングルスレッドで走る**（数倍遅い）。

回避策は Service Worker でヘッダを注入する手（`coi-serviceworker` 方式）だが、
**これは書影表示と衝突する。**

- `COEP: require-corp` は CORP ヘッダを返さないクロスオリジンの下位リソースを遮断する
- NDL の書影は `<img>` で CORS 無しに読んでいる（CLAUDE.md §5）。**これが止まる**
- `COEP: credentialless` なら no-cors の画像は通るが、Safari が対応していない

### 決定

> **スレッドは諦める。シングルスレッド前提で成立する構成にする。**
> `coi-serviceworker` は入れない。書影が消える代償に見合わない。

その代わり、シングルスレッドで間に合わせるための手を打つ。

- **OCR は Web Worker で走らせる**（並列化ではなく、カメラのプレビューと UI を止めないため）
- **1枚あたりの認識回数を削る** — 検出は1回、認識は背表紙ごとに1回。向きの試行は §6 で1本化する
- **量子化モデルを使う**（int8）。ダウンロード量と推論時間の両方に効く
- **WebGPU が使えれば使う**が、必須にしない。特徴検出して駄目なら wasm に落ちる

## 4. 「かざすだけ」を壊さない — 自動シャッター

CLAUDE.md §2 は「操作は『かざすだけ』。押すボタンは1つ」と決めている。
一方 §8 は「ライブカメラの映像を VLM に毎フレーム投げない」と決めている。
**端末内 OCR でも事情は同じで、1枚 1〜数秒かかるものを毎フレーム回すことはできない。**

シャッターボタンを置けば解決するが、それは「かざすだけ」を捨てることである。

### 決定

> **静止を検出して自動で1枚採る。ボタンは「カメラを起動」のままにする。**

```
毎フレーム（軽い処理のみ、160x120 に縮小した輝度で）
   ├─ 直前フレームとの差分 → 動いている？   → 何もしない
   ├─ 鮮鋭度（ラプラシアン分散相当）が低い → 何もしない（ブレ・ピント外れ）
   └─ 静止して鮮鋭 かつ 前回採用から一定間隔 → この1枚を採用 → Worker へ渡す
```

- 判定は**縮小したグレースケール上で行う**ので、毎フレームでも負荷は無視できる
- 採用した瞬間に**画面を光らせる／触覚で返す**。バーコード経路の `signalHit` と同じ扱いにする。
  「いま読んだ」が判らないと、利用者は同じ棚の前で待ち続ける
- OCR 中も**プレビューは止めない**。次の静止は OCR が終わるまで採らない（キューを溜めない）
- 採用フレームは `Photo` として IndexedDB に残す（ストアは既にある）。
  写真上のオーバーレイ確認（CONCEPT §6）と、モデル差し替え後の再 OCR に要る

### 撮影条件

バーコードと違って**解像度が精度を直接支配する**ので、要求を変える。

| | バーコード（現状） | 背表紙 |
|---|---|---|
| 要求解像度 | 1280x720 | 1920x1080 以上を `ideal` で要求 |
| 切り出し | 中央帯 45%（`grabCenterBand`） | **全画面**（新規 `grabFrame`） |
| ピント | 既定のまま | `focusMode: continuous` を可能なら指定 |

`ImageCapture.takePhoto()` が使えれば静止画の最大解像度を採る。
非対応（Safari 等）では映像フレームで代替する。

## 5. 背表紙の切り出しを OpenCV 抜きでやる

CONCEPT §2 は「(2) 切り出し = 縦エッジ検出」と書き、CLAUDE.md §8 は
「OpenCV.js を入れない（8MB超）」と決めている。この2つは矛盾しない。

**OCR の検出モデルが、既に回転した文字列の枠を返す。** 直線検出は要らない。
1本の背表紙に載った文字は、**背表紙の長軸に沿って一列に並ぶ**。
つまり切り出しは「枠を並びでまとめる」問題に落ちる。

```
       ┌──┬──┬──┬──┬──┐        det が返す枠（回転あり）を
       │▒▒│▒▒│▒▒│▒▒│▒▒│        長軸の法線方向に射影すると、
       │▒▒│  │▒▒│▒▒│  │        同じ背表紙の枠は同じ位置に集まる
       │  │▒▒│▒▒│  │▒▒│               │
       └──┴──┴──┴──┴──┘               ▼
        │  │  │  │  │              ┃  ┃ ┃   ┃  ┃    ← 谷で切る
        └──┴──┴──┴──┴─ 5本の背表紙
```

### アルゴリズム（`src/lib/spine/cluster.ts`、純関数）

1. 各 `quad` の中心・長軸角・長さを出す
2. **全体の傾きを枠の角度の中央値で推定する。** 棚を斜めから撮っても効くようにする
3. 長軸の**法線方向**へ中心を射影し、1次元の値にする
4. その1次元列を**間隔で分割**する（しきい値は枠の短辺の中央値に比例させる。
   絶対値で持つと解像度や距離が変わった瞬間に崩れる）
5. クラスタ内を長軸方向に並べる → **背表紙を上から下へ読んだ順の行列**になる
6. 捨てる: 文字数が極端に少ない／幅が他クラスタから大きく外れる／信頼度が低いものだけのクラスタ

**純関数なので、合成した枠の座標だけでテストできる。** 実写もモデルも要らない。
斜め・部分遮蔽・2段写り込みといったケースをフィクスチャで固定する。

> **横置きの本（平積み・寝かせた本）はこの前提から外れる。**
> 角度の中央値から大きく外れる枠は「別の並び」として独立クラスタにするが、
> 精度は落ちる。まず縦に並んだ本を当てることに集中し、横置きは §13 の計測で影響を測ってから判断する。

## 6. 向き — 90°回転と縦書き

背表紙の文字は2通りあり、**扱いが違う**。

| | 見え方 | 対処 |
|---|---|---|
| **横書きを90°倒したもの**（多数） | 文字が寝ている | 切り出しを90°回転すれば通常の行になる |
| **縦書き**（縦組みの書名・文庫の背） | 文字は正立、上から下へ積む | 90°回転すると文字が寝る。モデルの縦書き対応に頼る |

さらに90°回転は**左右2通り**あり、間違えると上下逆さの行を認識することになる。
つまり素朴にやると 1本の背表紙あたり最大3通り（±90°・回転なし）試すことになり、§3 の
シングルスレッド前提では重すぎる。

### 決定

> **背表紙ごとに1回だけ向きを決め、そのクラスタ内で使い回す。**

1. クラスタ内で**最も長い枠**を1つ選び、そこだけ ±90° の2通りを認識する
2. 平均信頼度が高い方を、そのクラスタの向きとして採用する
3. 残りの枠はその向きだけで認識する（試行は1通り）
4. 認識結果の平均信頼度がクラスタ全体で低ければ、回転なし（縦書き）で1回だけ再試行する

枠が1本しかないクラスタでは 1で決めた向きがそのまま結果になるので、余計な計算は増えない。
**1本あたりの認識回数は「枠の数 + 1」に収まる。**

## 7. OCR行 → 照合クエリ

クラスタは「文字列の並び」であって、まだ書誌ではない。
`ExtractedSpine`（`title` / `authors` / `publisher` / `confidence`）へ落とす必要がある。

背表紙には**タイトル以外のものが必ず載っている**。

```
  ┌────────────────────────────────┐
  │ 岩波文庫 ← レーベル             │  ← 出版社/レーベルは辞書で当てられる
  │ 吾輩は猫である ← タイトル       │  ← いちばん大きい・いちばん長い
  │ 夏目漱石 ← 著者                 │  ← 人名らしさ・末尾の「著」「訳」
  │ 岩波書店 ← 出版社               │
  │ ￥800E 33 ← 価格・分類          │  ← 捨てる
  └────────────────────────────────┘
```

### 割り当ての規則（`src/lib/spine/parse.ts`）

| 判定 | 根拠 |
|---|---|
| **捨てる** | 価格表記（`¥`/`円`/`E` 付きの数字）、数字だけ、1文字、記号だけ |
| **出版社・レーベル** | 小さな内蔵辞書に一致（岩波書店・岩波文庫・講談社現代新書 …） |
| **著者** | 末尾が「著」「訳」「編」「監修」/ 2〜5文字で人名らしい / 出版社辞書に当たらず短い |
| **タイトル** | 残りのうち**枠が最も大きいもの**。同程度なら最も長いもの |
| **巻次** | 既存の `splitTitle` に渡す（実装済み） |

**枠の大きさを使えるのが OCR 経路の利点である。** 背表紙ではタイトルが最大級の文字で入るので、
文字の大小という手がかりは強い。VLM 経路には無かった情報である。

**辞書は小さく保つ。** 主要出版社と文庫・新書レーベル、数百件で十分効く。
網羅を狙うと保守できないので、外れたものは「出版社不明」として通す。
出版社は照合スコアで弱い加点にしか使われない（`similarity.ts` の `matchScore`）ので、
外しても致命傷にならない設計に既になっている。

`confidence` は OCR の信頼度・タイトル文字数・枠の大きさから合成する。
**これが `AUTO_CONFIRM_THRESHOLD` の手前の関門になる**（`statusFromScore`）。

## 8. 照合の順序は経路で変える

ここが**既存コードに手を入れる唯一の箇所**である。

`resolveByTitle`（`pipeline/stages.ts`）は現在 **Google Books → NDL** の順で引く。
これは ISBN 経路の順序（openBD → Google Books → NDL）に合わせた並びだが、
**書名検索では正しくない。**

| ソース | 書名検索 | 和書カバレッジ |
|---|---|---|
| openBD | **できない**（ISBN引き専用） | 高 |
| Google Books | できる | **弱い**（CLAUDE.md §3、実測済み） |
| NDL サーチ | できる | **最強**（法定納本） |

CLAUDE.md §3 は「Google Books は日本語書籍のカバレッジが弱い」を実測された前提として扱っている。
**その前提を最初に当てるソースに置く理由が無い。**

### 決定

> **書名経路は NDL を先に当てる。当たらなければ Google Books。**
> **ISBN が確定したら openBD で補完する（書影・詳細）。**

```
ExtractedSpine
   │
   ▼
 NDL（書名+著者）──当たり──▶ 候補にスコア付け ──▶ ISBN が取れた？
   │外れ                                              │はい
   ▼                                                  ▼
 Google Books ──当たり──▶ 候補にスコア付け      openBD で補完（非破壊）
   │外れ                        │                     │
   ▼                            ▼                     ▼
 「見つからず」で残す      スコアで status を決める（confirmed / needsReview）
```

**ISBN 経路の順序は変えない。** openBD が1リクエストで最も速く当たるという判断は
ISBN 完全一致に対するものであって、この変更と競合しない。

**突合（`mergeNdlResult`）はそのまま使える。** 書名経路では NDL が一次結果になるので、
Google Books 側が後から差分を出す形に向きが入れ替わるだけである。非破壊・冪等の性質は変わらない。

### レート制限と待ち時間

棚1枚で 20〜40 冊が同時に入る。既存の直列キュー（`LOOKUP_INTERVAL_MS = 260`）のままなら
全件で 10〜30 秒かかる。**これは許容する**（行は先に出るので一覧は空にならない）が、
無駄打ちは削る。

- **統合（§9）を照合の前に置く。** 同じ本を2回引かない
- **正規化クエリでキャッシュする**（メモリ + IndexedDB）。棚を戻って写しても再問い合わせしない。
  NDL 中継は Worker 側で1日キャッシュしているが、往復自体を無くす方が速い

---

## 9. 同じ背表紙を何度も読む前提で統合する

棚にかざして動かせば、同じ本が何度も入る。CONCEPT §6 の「複数枚の統合」を
**フレーム単位でやることになる**ので、要求が上がる。

### 決定

> **統合の鍵は3段。上から順に当てる。**

| 優先 | 鍵 | 扱い |
|---|---|---|
| 1 | 確定した `isbn13` | 同一。無条件で統合する |
| 2 | 正規化した「書名+著者」（`normalizeForMatch`） | 同一とみなす |
| 3 | 正規化した OCR 生テキストの類似度（`titleSimilarity` ≥ しきい値） | **同一候補**。統合するが、統合したことを記録する |

**誤マージは取りこぼしより痛い**（CONCEPT §10）。上下巻・シリーズの隣接巻は
背表紙がほぼ同じで、3の鍵は必ず誤爆する。だから3では巻次（`splitTitle` の `volume`）が
食い違うものを別扱いにする。

統合時の振る舞いは**既存の非破壊の原則をそのまま延ばす**。

- 候補は消さず `candidates` に足す
- **読み取り回数（`sightings`）を数える。** 同じ本を3回別のフレームから読めたなら、
  1回だけのものより確度が高い。`confidence` の底上げに使う
- **OCR 結果は「文字数が多く信頼度が高い方」を採る。** 部分的に写った背表紙より、
  正面から写ったものを優先する
- `pinned` と `excluded` には触れない。**一度除外した本が、次のフレームで復活しては困る**

---

## 10. 判断は要る。操作は増やさない

CLAUDE.md §4 は段階ボタンを外した理由を
「バーコードで読んだ本には、人間が判断できることが何も無い」と書いている。
**背表紙経路はここが違う。** OCR は誤読するし、書名照合は別の本を引く。
人間の判断は要る。

だが**判断が要ることと、操作を増やすことは別である。**
§4 が本当に嫌っていたのは「押し忘れれば成果がゼロになる状態」であって、確認そのものではない。

### 決定

> **読み取りと照合は全自動のまま。確認は一覧の中で完結させる。専用画面を作らない。**

- 読んだ端から行が増える。書名は後から埋まる（バーコード経路と同じ体験）
- `confirmed` は黙って確定。**全件確認させない**
- `needsReview` / `conflict` だけ候補ボタンを開く。**`BookList` に実装済み**（`showCandidates`）
- `notFound` は「バーコードで読み直す」導線を出す。**背表紙で読めない本の救済はバーコードである**

追加が要るのは「要確認だけを見たい」という絞り込みで、
既存の `summary` チップを押せるようにするだけで足りる。新しい画面は要らない。

## 12. 型の追加

既存の `ExtractedSpine` は**そのまま合流点として使える**（`title` / `authors` / `publisher` /
`confidence` / `box`）。足すのは読み取り側の型と、統合のための2フィールドだけ。

```ts
/** 回転した枠。矩形の box では背表紙を表せない */
export interface Quad { p: readonly [Point, Point, Point, Point] }

export interface ExtractedSpine {
  // ... 既存 ...
  /** OCR が返した行そのまま。デバッグと再解釈のために捨てない */
  lines?: string[]
  /** 回転した枠。box は互換のため残し、その外接矩形を入れる */
  quad?: Quad
}

export interface BookEntry {
  // ... 既存 ...
  /** 別のフレームから同じ本を読んだ回数（§9）。確度の底上げに使う */
  sightings?: number
  /** 統合の鍵。どの鍵で束ねたかを残す（誤マージの調査に要る） */
  mergeKey?: { kind: 'isbn' | 'titleAuthor' | 'similar'; value: string }
}
```

**どちらも省略可能にする。** IndexedDB は `DB_VERSION = 1` のまま、
既存レコードを読んでも壊れない。**索引を張りたくなったときだけ版を上げる。**

## 13. 実測の枠組みと、中止条件

CLAUDE.md §9 は「精度の実測」を次の一手に挙げている。
**この経路では実測が先である。後回しにできない。**
OCR が当たらなければ §5〜§10 をどれだけ作り込んでも成果はゼロで、
しかも「作り込みが足りないのか、そもそも読めないのか」が区別できなくなる。

### 測り方

```
eval/fixtures/<棚の名前>/
  shelf.jpg          棚1段の写真
  truth.json         写っている本の正解（title / authors / isbn13）
eval/run.ts          OCR → クラスタ → クエリ組み立て まで走らせ、正解と突き合わせる
```

- **照合（外部API）は差し替える。** ローカルの固定データで代替し、OCR の質だけを測る。
  この環境から外部へ出られない（CLAUDE.md §7）ので、これは制約ではなく前提である
- 正解データは、写真から**バーコードで読んで作る**。既存経路がそのまま治具になる
- 指標は3つ。**混ぜない**

| 指標 | 定義 |
|---|---|
| **検出率** | 写っている本のうち、背表紙として切り出せた割合（§5 まで） |
| **再現率** | 写っている本のうち、正解の書誌に到達した割合（§8 まで） |
| **誤確定率** | `confirmed` にしたもののうち、別の本だった割合 |

### 先に決めておく中止条件

**「やってみて駄目だったから引き返す」を、駄目になってから決めない。**

| 結果 | 判断 |
|---|---|
| 再現率 ≥ 60% かつ 誤確定率 ≤ 2% | この設計で進める |
| 検出率は高いが再現率が低い | OCR ではなく §7/§8 の問題。クエリ組み立てと照合順序を直す |
| 検出率が低い | **OCR の限界。** エンジンを差し替えて再測（`OcrEngine` の口が効く） |
| どのエンジンでも再現率 < 40% | **ブラウザ内 OCR では届かない。** §1 に戻り、ネイティブ殻＋ML Kit を判断する |
| 誤確定率 > 5% | しきい値ではなく統合（§9）を疑う。誤マージは取りこぼしより痛い |

**60% という数字自体は仮である。** ただ、棚1段20冊で12冊当たり、残りをバーコードで拾うなら
手入力よりは速い ── その程度の根拠しかない。**最初の実測で置き換えるべき数字である。**

## 14. 段取り

**各段の終わりに測る。** 測らずに次へ行かない。

| 段 | 作るもの | 終了条件 |
|---|---|---|
| **P0** | `eval/` の器と正解データ1棚ぶん。`OcrEngine` の口と PP-OCRv5 実装 | **写真1枚から行が取れる。** ここで初回DL量と1枚あたりの時間を測る（§3） |
| **P1** | クラスタリング（§5）・向き（§6）・クエリ組み立て（§7）。すべて純関数＋単体テスト | 検出率と、OCR 単体の文字精度が数字で出る |
| **P2** | `resolveByTitle` の順序変更（§8）・統合（§9）・照合キャッシュ | **再現率と誤確定率が出る。§13 の中止条件で判断する** |
| **P3** | `SpineScanner`（§4）・一覧の絞り込み（§10）。タブを実接続 | 棚にかざして一覧ができる |

**P0〜P2 はカメラを使わない。** 写真とフィクスチャだけで進む。
つまり**この開発環境で最後まで検証できる**。カメラが要るのは P3 だけで、
そこは Playwright と `getUserMedia` の差し替えで通し確認する（CLAUDE.md §7 の手と同じ）。

**P3 を最後に置いたのは意図的である。** 先に UI を作ると、
読めないのが撮影のせいなのか OCR のせいなのか判らなくなる。

## 15. この経路について「やらない」と決めること

- **設定画面を作らない。** OCR エンジンの選択肢も出さない。
  自動で決まらないものは設計が終わっていないということである（CLAUDE.md §2）
- **シャッターボタンを置かない。** §4 の自動シャッターが機能しないなら、
  それは判定の作り直しであってボタンの追加ではない
- **OpenCV.js を入れない。** §5 で不要にした。それでも切り出しが足りないなら、
  det モデルの入力解像度を上げる方を先に試す
- **毎フレーム OCR しない。** §4 の通り
- **貼り付け経路を作らない。** iOS のライブテキストや Google レンズで読んだ文字列を
  貼り込む口は、実装はほぼゼロで精度は最高になる。**が、これは撤去した
  チャットAI経路と同じ形である**（手作業の往復）。同じ理由で採らない。
  ただし **§13 の正解データ作成には使ってよい**（開発用の治具であって機能ではない）
- **横置きの本を最初から狙わない。** §5 の通り、まず縦に並んだ本を当てる

## 16. 未検証の前提

**この文書の中で、実地で確かめていないもの。** CONCEPT §10 の表と同じ扱いで持つ。

| 項目 | 状況 |
|---|---|
| ML Kit に Web/JS 実装が無い | 調査で確認（公式ドキュメントと複数の二次情報が一致） |
| GitHub Pages が COOP/COEP を設定できない | 調査で確認。`coi-serviceworker` 回避策の存在も確認 |
| `COEP: require-corp` が NDL 書影を止める | 仕様上そうなる。**実地未確認**（採らない判断なので確認しない） |
